# AGENTS.md - AI 编码代理规范模板

> 本模板定义了 AI 编码代理在项目中的行为准则。
> 使用时请根据具体项目进行配置。

## 开发流程规范（文档驱动开发）

**核心原则**: 文档先行，代码跟随，测试验证，文档收尾。

### 开发周期

每个功能/修改都必须遵循以下流程：

```
┌─────────────────────────────────────────────────────────────────┐
│  1. 文档准备阶段                                                   │
│     ├── 更新/创建设计文档 (docs/design/)                          │
│     ├── 更新 ROADMAP.md (如果是新功能)                            │
│     └── 更新 Story 文件 (stories/)                                │
├─────────────────────────────────────────────────────────────────┤
│  2. 编码阶段                                                       │
│     ├── 实现功能代码                                               │
│     ├── 添加代码注释                                               │
│     ├── 同步更新 docs/ 对应文档（必须！）                          │
│     └── 更新模块文档                                               │
├─────────────────────────────────────────────────────────────────┤
│  3. 测试阶段                                                       │
│     ├── 单元测试                                                   │
│     ├── 集成测试                                                   │
│     └── 示例测试                                                   │
├─────────────────────────────────────────────────────────────────┤
│  4. 文档收尾阶段                                                   │
│     ├── 更新 CHANGELOG.md                                         │
│     ├── 更新 API 文档 (如有变化)                                   │
│     └── 更新 README.md (如有用户可见变化)                          │
└─────────────────────────────────────────────────────────────────┘
```

### 阶段详解

#### 1. 文档准备阶段

在写任何代码之前，必须先准备文档：

```markdown
# 检查清单

- [ ] 功能是否已在 ROADMAP.md 中规划？
- [ ] 是否需要新的设计文档 (RFC)？
- [ ] Story 文件是否已创建/更新？
- [ ] API 覆盖分析是否需要更新？
```

**需要创建/更新的文档**：

| 场景 | 需要更新的文档 |
|------|---------------|
| 新功能 | ROADMAP.md, Story 文件, 设计文档 |
| Bug 修复 | Story 文件, CHANGELOG.md |
| API 变更 | api-coverage.md, 类型文档 |
| 新类型 | types.md, 对应的类型文档 |

#### 2. 编码阶段

编码时同步更新相关文档：

```
/// 每个公共 API 必须有文档注释
///
/// 示例:
/// ```
/// const result = api.doSomething(args);
/// ```
pub fn doSomething(args: Args) Result {
    // 实现...
}
```

**编码后立即更新**：
- 模块文档
- API 使用示例
- 代码内注释

#### 3. 测试阶段

测试分三个层次：

```bash
# 1. 单元测试 - 测试单个模块
${test_single_module_cmd}

# 2. 集成测试 - 测试整个项目
${test_cmd}

# 3. 示例测试 - 验证用户场景
${run_examples_cmd}
```

### 测试质量要求（强制）

**核心原则**: 所有测试必须通过，无内存泄漏（适用语言）、无崩溃。

#### 必须满足的条件

1. **所有测试通过**: 测试命令必须 100% 通过
2. **无资源泄漏**: 内存、文件句柄、网络连接等必须正确释放
3. **无崩溃**: 测试不能崩溃或产生未定义行为

#### 提交前测试检查清单

```markdown
# 测试检查清单

- [ ] 单元测试通过
- [ ] 集成测试通过
- [ ] 无资源泄漏
- [ ] 无崩溃
- [ ] 新代码有对应的测试
- [ ] 测试覆盖正常路径和错误路径
```

#### 4. 文档收尾阶段

每次开发完成后必须更新：

```markdown
# CHANGELOG.md 更新模板

### Session YYYY-MM-DD-NNN

**日期**: YYYY-MM-DD
**目标**: 简要描述

#### 完成的工作
1. ...
2. ...

#### 测试结果
- 单元测试: X tests passed
- 集成测试: passed/failed

#### 下一步
- [ ] ...
```

## 文档同步更新规范（强制）

**核心原则**: 代码和文档必须同步更新，不允许代码实现后文档滞后。

### docs/ 目录结构镜像 src/

```
src/                          docs/
├── module_a/                 ├── module_a/
│   ├── file1.ext            │   ├── file1.md
│   └── file2.ext            │   └── file2.md
├── module_b/                 ├── module_b/
│   └── ...                  │   └── ...
└── ...                       └── ...
```

### 文档更新触发条件

| 代码变更类型 | 必须更新的文档 |
|-------------|---------------|
| 新增模块 | `docs/<module>/README.md` + 各文件对应的 `.md` |
| 新增类型 | 类型文档 + 设计文档 |
| 新增 API 端点 | API 覆盖文档 |
| 新增公共函数 | 对应模块的文档 |
| 修改函数签名 | 对应模块的文档 |
| 修改行为/逻辑 | 对应模块的文档 |
| 新增错误类型 | 错误文档 |
| Story 完成 | ROADMAP.md 对应任务标记 ✅ |

### ROADMAP.md 更新规范（强制）

**ROADMAP.md 是项目的唯一真相来源**，必须始终保持最新状态。

#### 必须更新 ROADMAP.md 的场景

| 场景 | 更新内容 |
|------|----------|
| Story 开始 | 对应 Story 状态改为 🔨 进行中 |
| Story 完成 | 对应 Story 状态改为 ✅ 已完成 |
| 版本完成 | 当前状态部分更新版本号和阶段状态 |
| 新增功能实现 | 对应功能状态从 ⏳ 改为 ✅ |

## 阶段完成前检查规范（强制）

**核心原则**: 在开始下一个版本阶段之前，必须检查并解决之前版本的遗留问题。

### 阶段完成检查流程

```
┌─────────────────────────────────────────────────────────────────┐
│  1. 全面文档扫描（查找所有未完成标记）                              │
│     ├── ROADMAP.md - 检查 ⏳ 状态的功能                          │
│     ├── stories/*.md - 检查 [ ] 未勾选的任务                      │
│     ├── docs/**/*.md - 检查 TODO、FIXME、⏳ 标记                  │
│     └── 代码注释 - 检查 TODO、FIXME、XXX 标记                     │
├─────────────────────────────────────────────────────────────────┤
│  2. 分类和评估遗留问题                                             │
│     ├── 当前版本遗留 - 必须决定：完成/推迟/取消                   │
│     ├── 之前版本遗留 - 评估是否可以顺便解决                       │
│     └── 记录所有决定和原因                                        │
├─────────────────────────────────────────────────────────────────┤
│  3. 解决可处理的遗留问题                                           │
│     ├── 实现功能                                                   │
│     ├── 添加测试                                                   │
│     └── 更新相关文档                                              │
├─────────────────────────────────────────────────────────────────┤
│  4. 运行完整测试验证                                               │
├─────────────────────────────────────────────────────────────────┤
│  5. 同步更新所有文档状态                                           │
│     ├── ROADMAP.md - 版本状态、变更日志                           │
│     ├── stories/*.md - 任务完成状态                               │
│     └── 代码注释 - 清理已解决的 TODO/FIXME                        │
└─────────────────────────────────────────────────────────────────┘
```

### 文档扫描命令

```bash
# 1. 扫描 ROADMAP.md 中的待办项
grep -n "⏳" ROADMAP.md

# 2. 扫描 stories/ 中未完成的任务
grep -rn "\[ \]" stories/
grep -rn "⏳" stories/

# 3. 扫描 docs/ 中的 TODO 和未完成标记
grep -rn "TODO\|FIXME\|⏳\|\[ \]" docs/

# 4. 扫描代码中的 TODO 和 FIXME
grep -rn "TODO\|FIXME\|XXX" src/

# 5. 一键扫描所有
echo "=== ROADMAP.md ===" && grep -n "⏳" ROADMAP.md && \
echo "=== stories/ ===" && grep -rn "\[ \]\|⏳" stories/ && \
echo "=== docs/ ===" && grep -rn "TODO\|FIXME\|⏳\|\[ \]" docs/ && \
echo "=== src/ ===" && grep -rn "TODO\|FIXME\|XXX" src/
```

### 未完成标记说明

| 标记 | 位置 | 含义 |
|------|------|------|
| `⏳` | ROADMAP.md, stories/, docs/ | 待开始或进行中 |
| `🔨` | ROADMAP.md, stories/ | 正在进行中 |
| `[ ]` | stories/, docs/ | 未完成的检查项/任务 |
| `TODO` | 代码注释, docs/ | 待实现的功能 |
| `FIXME` | 代码注释, docs/ | 需要修复的问题 |
| `XXX` | 代码注释 | 需要注意或重构的代码 |

### 遗留问题处理原则

| 优先级 | 处理方式 |
|--------|----------|
| 高 - 阻塞后续功能 | 必须在当前阶段解决 |
| 中 - 独立功能且工作量小 | 顺便解决，提高完成度 |
| 中 - 独立功能但工作量大 | 记录并推迟到下个版本 |
| 低 - 边缘功能 | 记录并推迟，不影响版本完成 |
| 无效 - 不再需要 | 移除标记，更新文档说明原因 |

### 阶段完成标准

只有满足以下所有条件，才能标记版本为"已完成"：

1. **当前版本核心功能 100% 完成**（非核心功能可推迟）
2. **所有测试通过**
3. **文档状态同步**
4. **遗留问题已评估并记录**

## 文档更新前验证规则（强制）

**核心原则**: 在更新任何文档状态标记之前，必须先验证代码已完全实现。

### 验证流程

在将任何 `⏳` 改为 `✅` 或 `[ ]` 改为 `[x]` 之前，必须：

```
┌─────────────────────────────────────────────────────────────────┐
│  1. 确认代码文件存在                                               │
│     ├── 检查对应的源文件是否已创建                                 │
│     ├── 检查模块是否已正确导出                                     │
│     └── 检查类型/函数是否已正确导出                               │
├─────────────────────────────────────────────────────────────────┤
│  2. 确认功能已实现                                                 │
│     ├── 检查函数/方法是否有完整实现（非空壳）                     │
│     ├── 检查核心逻辑是否完整                                      │
│     └── 检查错误处理是否完整                                      │
├─────────────────────────────────────────────────────────────────┤
│  3. 确认测试存在且通过                                             │
│     ├── 检查对应的测试是否已编写                                  │
│     ├── 运行测试确认通过                                          │
│     └── 确认无资源泄漏                                            │
├─────────────────────────────────────────────────────────────────┤
│  4. 更新文档状态                                                   │
│     ├── 只有以上全部确认后才能更新状态                            │
│     └── 同时更新所有相关文档（ROADMAP, Story, docs/）             │
└─────────────────────────────────────────────────────────────────┘
```

### 禁止行为

❌ **禁止**: 在代码未实现时就更新文档状态为"已完成"
❌ **禁止**: 只实现了部分功能就标记整个模块为"已完成"
❌ **禁止**: 测试未通过就更新文档状态
❌ **禁止**: 只更新部分文档（如只更新 ROADMAP 不更新 Story）

## 代码风格规范

### 命名约定

```
# 类型名: PascalCase
MyStruct, ClientState, OrderType

# 函数和变量: camelCase 或 snake_case（根据语言惯例）
processOrder, order_count

# 常量: SCREAMING_SNAKE_CASE
MAX_RETRIES, DEFAULT_TIMEOUT

# 文件名: snake_case
order_builder, http_client
```

### 文档注释

所有公共 API 必须有文档注释：

```
/// 函数功能描述
///
/// 参数:
///   - param1: 参数说明
///   - param2: 参数说明
///
/// 返回: 返回值说明
/// 错误: 可能的错误
pub fn functionName(param1: Type1, param2: Type2) Result {
    // ...
}
```

## 资源管理

### 资源清理原则

```
# 所有资源必须有对应的清理逻辑
resource = acquire()
defer cleanup(resource)  # 或语言对应的清理机制

# 使用 RAII 或 defer/finally 模式
# 错误路径也必须正确清理资源
```

### 错误处理

```
# ❌ 错误 - 静默忽略错误
result = doSomething() or null

# ✅ 正确 - 传播或处理错误
result = try doSomething()

# ✅ 正确 - 有意义的错误处理
result = doSomething() catch |err| {
    log.error("Failed: {}", err)
    return err
}
```

## 项目特定规则模板

### 敏感数据处理

```
# ❌ 错误 - 原始敏感数据
credentials = {
    secret: raw_secret,  # 可能被意外打印
}

# ✅ 正确 - 使用包装类型
credentials = {
    secret: Secret(raw_secret),  # 打印时显示 [REDACTED]
}
```

### 精确计算（金融/科学计算）

```
# ❌ 永远不要用浮点数处理精确计算
price = 0.65
total = price * 100  # 可能是 64.99999999...

# ✅ 正确 - 使用精确计算类型
price = Decimal("0.65")
total = price * Decimal("100")  # 精确的 65.00
```

### 安全日志

```
# ❌ 错误 - 泄露敏感信息
log.info("API Key: {}", credentials.key)

# ✅ 正确 - 安全日志
log.info("Request to {}", endpoint)
log.debug("Order ID: {}", order_id)
```
